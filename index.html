Kar Trust Layer settlement that waits for proof
Start herePlain wordsThe runTry itHow it worksBlueprintFor your businessWhite paperDocs

An AI agent should pay only for checked work, and never pay an attacker.

Kar Trust Layer is settlement for agent commerce, built for QDay Aevum testnet. An agent with an ERC-8004 identity takes a job from Fallmarket through a session key it cannot exceed. A worker delivers an answer made only of words copied from the job's sources. The DocDec verifier signs off, and the FulfilmentGate releases tUSD8 only after the chain rebuilds the answer from the cited bytes of those sources and finds it identical. A prompt injection that tells the agent to pay someone else is refused by the chain, even when the agent obeys it.

The quote is re-checked on-chain

In plain words

ERC-8004 identitya public, on-chain ID card for an AI agent (an NFT), with the address where it is paid. Here: the buyer agent, the worker and the verifier each have one.
Smart accounta wallet that is a program: it holds the agent's money and decides which signed requests it will obey.
Session keya second key the owner gives the agent. The account lets it spend only up to a cap, only until an expiry, and only to listed recipients. The owner can revoke it in one transaction. The owner's own key never touches the agent.
Escrowmoney held by the FulfilmentGate contract until the job is proven done (paid to the worker) or failed or late (back to the buyer).
Copy-only answerthe worker may only copy phrases that are really in the sources, and must say where each starts and ends (byte offsets). Paraphrase is not allowed.
DocDec verifieran agent that checks the answer is exactly those copied bytes and that it addresses the question, then signs PASS (100) or FAIL (0) on-chain.
tUSD8 / tQDAYQDay's test dollar and test gas token. No monetary value.

The sources, with the cited bytes marked

Three verbatim excerpts of the ERC-8004 spec (CC0). Their hashes are committed on-chain when the job opens.

source 0: ERC-8004: Identity Registry (excerpt) · 1389 bytes
### Identity Registry The Identity Registry uses ERC-721 with the URIStorage extension for agent registration, making **all agents immediately browsable and transferable with NFTs-compliant apps**. Each agent is uniquely identified globally by: * *agentRegistry*: A colon-separated string `{namespace}:{chainId}:{identityRegistry}` (e.g., `eip155:1:0x742...`) where: * *namespace*: The chain family identifier (`eip155` for EVM chains) * *chainId*: The blockchain network identifier * *identityRegistry*: The address where the ERC-721 registry contract is deployed * *agentId*: The ERC-721 tokenId assigned incrementally by the registry Throughout this document, *tokenId* in ERC-721 is referred to as *agentId* and *tokenURI* in ERC-721 is referred to as *agentURI*. The owner of the ERC-721 token is the owner of the agent and can transfer ownership or delegate management (e.g., updating the registration file) to operators, as supported by `ERC721URIStorage`. #### Agent URI and Agent Registration File The *agentURI* MUST resolve to the agent registration file. It MAY use any URI scheme such as `ipfs://` (e.g., `ipfs://cid`), `https://` (e.g., `https://example.com/agent3.json`), or a base64-encoded `data:` URI (e.g., `data:application/json;base64,eyJ0eXBlIjoi...`) for fully on-chain metadata. When the registration uri changes, it can be updated with *setAgentURI()*.
source 1: ERC-8004: On-chain metadata and the agent wallet (excerpt) · 1613 bytes
#### On-chain metadata The registry extends ERC-721 by adding `getMetadata(uint256 agentId, string metadataKey)` and `setMetadata(uint256 agentId, string metadataKey, bytes metadataValue)` functions for optional extra on-chain agent metadata: ```solidity function getMetadata(uint256 agentId, string memory metadataKey) external view returns (bytes memory) function setMetadata(uint256 agentId, string memory metadataKey, bytes memory metadataValue) external ``` When metadata is set, the following event is emitted: ```solidity event MetadataSet(uint256 indexed agentId, string indexed indexedMetadataKey, string metadataKey, bytes metadataValue) ``` The key `agentWallet` is reserved and cannot be set via `setMetadata()` or during `register()` (including the metadata array overload). It represents the address where the agent receives payments and is initially set to the owner's address. To change it, the agent owner must prove control of the new wallet by providing a valid [EIP-712](./eip-712.md) signature for EOAs or [ERC-1271](./eip-1271.md) for smart contract wallets—by calling: ```solidity function setAgentWallet(uint256 agentId, address newWallet, uint256 deadline, bytes calldata signature) external ``` To read and clear the currently set wallet, the following functions are exposed: ```solidity function getAgentWallet(uint256 agentId) external view returns (address) function unsetAgentWallet(uint256 agentId) external ``` When the agent is transferred, `agentWallet` is automatically cleared (effectively resetting it to the zero address) and must be re-verified by the new owner.
source 2: ERC-8004: Validation Registry (excerpt) · 3650 bytes
### Validation Registry **This registry enables agents to request verification of their work and allows validator smart contracts to provide responses that can be tracked on-chain**. Validator smart contracts could use, for example, stake-secured inference re-execution, zkML verifiers or TEE oracles to validate or reject requests. When the Validation Registry is deployed, the *identityRegistry* address is set via `initialize(address identityRegistry_)` and is visible by calling `getIdentityRegistry()`, as described above. #### Validation Request Agents request validation by calling: ```solidity function validationRequest(address validatorAddress, uint256 agentId, string requestURI, bytes32 requestHash) external ``` This function MUST be called by the owner or operator of *agentId*. The *requestURI* points to off-chain data containing all information needed for the validator to validate, including inputs and outputs needed for the verification. The *requestHash* is a commitment to this data (`keccak256` of the request payload) and identifies the request. All other fields are mandatory. A ValidationRequest event is emitted: ```solidity event ValidationRequest(address indexed validatorAddress, uint256 indexed agentId, string requestURI, bytes32 indexed requestHash) ``` #### Validation Response Validators respond by calling: ```solidity function validationResponse(bytes32 requestHash, uint8 response, string responseURI, bytes32 responseHash, string tag) external ``` Only *requestHash* and *response* are mandatory; *responseURI*, *responseHash* and *tag* are optional. This function MUST be called by the *validatorAddress* specified in the original request. The *response* is a value between 0 and 100, which can be used as binary (0 for failed, 100 for passed) or with intermediate values for validations with a spectrum of outcomes. The optional *responseURI* points to off-chain evidence or audit of the validation, *responseHash* is its commitment (in case the resource is not on IPFS), while *tag* allows for custom categorization or additional data. validationResponse() can be called multiple times for the same *requestHash*, enabling use cases like progressive validation states (e.g., “soft finality” and “hard finality” using *tag*) or updates to validation status. Upon successful execution, a *ValidationResponse* event is emitted with all function parameters: ```solidity event ValidationResponse(address indexed validatorAddress, uint256 indexed agentId, bytes32 indexed requestHash, uint8 response, string responseURI, bytes32 responseHash, string tag) ``` The contract stores *requestHash*, *validatorAddress*, *agentId*, *response*, *responseHash*, *lastUpdate*, and *tag* for on-chain querying and composability. #### Read Functions ```solidity function getValidationStatus(bytes32 requestHash) external view returns (address validatorAddress, uint256 agentId, uint8 response, bytes32 responseHash, string tag, uint256 lastUpdate) //Returns aggregated validation statistics for an agent. agentId is the only mandatory parameter; validatorAddresses and tag are optional filters function getSummary(uint256 agentId, address[] calldata validatorAddresses, string tag) external view returns (uint64 count, uint8 averageResponse) function getAgentValidations(uint256 agentId) external view returns (bytes32[] memory requestHashes) function getValidatorRequests(address validatorAddress) external view returns (bytes32[] memory requestHashes) ``` Incentives and slashing related to validation are managed by the specific validation protocol and are outside the scope of this registry.

How it works

The diagram is filled in from the run above: the amounts and the transaction hashes are that run's.

  1. Identity. Three agents register in the ERC-8004 Identity Registry. The buyer agent's agentWallet is bound to its smart account by an ERC-1271 signature, so the gate knows which account speaks for that identity.
  2. The wall. The account's owner grants a session key: a spend cap, an expiry and a recipient allowlist, written into the account. The agent holds only this key. It signs typed actions, and anyone may relay them.
  3. The job. A worker agent lists a job on Fallmarket with a price and the validator that must sign off. The agent takes it: the account approves exactly the price and the gate escrows it, together with the hash of the question and of every source document.
  4. The attack. The listing's terms carry a prompt injection. The run assumes the worst, that the model obeyed: the session key signs "pay 0xBAD… 10,000". The account refuses (RecipientNotAllowed). Routed through the one allowed recipient, the cap refuses it (OverCap).
  5. The work. The worker's copy-only reader picks the sentence that best covers the question and copies it, with its byte offsets. It cannot write a word that is not in a source.
  6. The verdict. The DocDec verifier checks that the answer is exactly the cited bytes and that it addresses the question, then signs 100 (PASS) or 0 (FAIL) for that exact deliverable in the ERC-8004 Validation Registry.
  7. Settlement. release pays only if the job's own validator signed PASS for the job's own worker, and the chain re-runs the verbatim check: sources hash to the committed root, answer equals the cited bytes. A FAIL refunds the buyer. Anyone can prune a listing whose worker's verified record falls under 60/100.

For your business

What it does for a firm whose AI agents buy work from other agents, and how to roll it out. Supplied by AI Native Solutions.

CEO

Your agents can buy work without a person approving each payment, and without a new way to lose money. Every payment is tied to a checked deliverable and a public record.

CFO

Escrow until proof: no payment for ungrounded work, a refund on a FAIL, nothing stranded. A hard cap per agent key, enforced by the chain, not by a policy document.

COO

The check that a person does today (does this answer really come from our documents?) runs on every job, at once, the same way every time.

CTO / CISO

The agent holds only a scoped key. A prompt injection can make the model sign a payment; it cannot make the chain execute it. Every rule is open source and mutation-tested.

Finance operations

One audit trail per job: escrow, deliverable hash, verifier's verdict, release or refund, each a transaction with a hash an auditor can check without asking you.

Engineering

An SDK and five contracts, MIT. Drop the verifier rule into your own agent, or use the gate as is. Runs on any Shanghai-level EVM chain.

Security, compliance, data

  • Keys: the agent never holds the owner key. Session keys are scoped and revocable at once; a key is never re-granted, so old signatures cannot return.
  • Data: sources are committed as hashes when a job opens. At release, the cited sources' bytes go on-chain as calldata, so use sources you can publish (public documents, a contract both sides hold). Confidential corpora belong on a permissioned deployment.
  • Personal data: none is needed. Agent identities are addresses and a registration file.
  • Assurance: every contract and kernel passes a mutation gate in CI; claims are sealed before runs.

Risks, answered straight

  • A dishonest verifier? It cannot pass a reworded answer: the chain re-checks the verbatim rule. It can wrongly FAIL work, which refunds the buyer; pick validators with a record (the Validation Registry keeps it).
  • A front-runner claims a request hash? They cannot be paid and cannot get the job paid; the worker resubmits, or the buyer is refunded at the deadline.
  • Testnet only today. This entry uses test tokens with no value. A production deployment is a fresh deployment of the same contracts on the chain you choose, with its own audit.

Questions buyers ask

What if the worker never delivers?Nothing is paid. After the job's deadline (at most 7 days, set when the job opens) anyone can call refund and the escrow returns to the buyer's account.
What if a paid answer later turns out wrong?The gate proves the answer's words are the sources' words, at the stated places, and that the verifier judged it on-question. It does not prove the sources are right. That boundary is stated, not hidden; the verifier's public record and the market's prune rule push out workers who game it.
Who can dispute a verdict?A worker who gets a FAIL may resubmit before the deadline; the buyer can take a refund as soon as the current deliverable has a FAIL. There is no arbitration layer: the verdict belongs to the validator the listing named, and every verdict is on-chain against its identity.
Who controls the sources?The buyer. Their hashes are fixed on-chain when the job opens; the worker cannot change them, and release reverts (SourcesMismatch) if the documents presented differ by one byte.
What if the session key is stolen?The thief gets what the agent had: the remaining cap, to allowlisted recipients only, until expiry. The owner revokes the key in one transaction (step S11 of the run shows the next attempt refused).
What if the verifier is compromised?It cannot get a reworded answer paid: the chain re-checks the words. It could pass a verbatim copy that is off the question, the one judgement the chain cannot re-run; that is bounded by the job's price and recorded against its identity.

White paper: settlement that waits for proof

Agent commerce has two failure modes that payments alone do not fix. The first is paying for work nobody checked: an agent buys an answer and the money moves whether or not the answer came from anywhere. The second is paying the wrong party: an agent reads untrusted text, and a prompt injection in it asks for a payment. Both are usually handled by a person approving payments, which is the step agents were meant to remove.

This build moves both rules into contracts. Payment is fulfilment-gated: the escrow opens against a commitment to the question and to the exact source documents, and closes only when two independent checks agree. The first is the verifier's signed verdict in the ERC-8004 Validation Registry. The second is the chain's own re-run of the part of that verdict it can compute: that the answer is exactly the cited byte ranges of the committed sources. The verifier's judgement (does the copied text address the question?) cannot be re-run on-chain, so it is signed, attributable and recorded against the verifier's identity, and a market rule removes workers whose record falls.

Spending is scoped at the key. The agent never holds the account's owner key. It holds a session key whose cap, expiry and allowlist live in the account, and every action it signs is checked against them before a token moves. The run tests this the hard way: it assumes the agent obeyed the injection and signed the payment, and shows the chain refusing it.

DocDec, measured

The verifier rule here is DocDec's verbatim-grounding property: every answer's exact words sit at checkable offsets. DocDec v2 pre-registered eight claims before its benchmark ran, and scored them as follows.

Those are DocDec's benchmark results, published on the DocDec demo; this build does not re-claim them. The three failures stay on the record as measured. Here, the worker is a copy-only reader and the verifier applies the verbatim and on-question rule.

What this proves, and what it does not. It proves the paid answer's words sit at their cited byte offsets in the sources the buyer committed to, and that the named verifier signed off. It does not prove the answer is the best one, that the sources are true, or that the worker understood them. Offsets are UTF-8 bytes. At release, the cited sources go on-chain as calldata. The explorer's contract verifier is not working yet, so the exact bytecode is published in artifacts/ for anyone to recompile and compare.
